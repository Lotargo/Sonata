# Процедурная память Sonata

> Статус: одобренное архитектурное решение  
> Назначение: определить внутренний механизм автоматической активации инструкций до запуска когнитивной перспективы  
> Связанный документ: `SONATA_COGNITIVE_MODEL.md`

## 1. Определение

Процедурная память Sonata - это лёгкий внутренний слой поиска, который подбирает подходящую инструкцию для конкретной перспективы и стадии до обращения к языковой модели.

Перспектива не должна самостоятельно просматривать реестр инструкций, рассуждать о выборе роли или решать, какой способ мышления ей применить. К моменту начала генерации необходимая инструкция уже должна быть найдена, проверена и встроена в собранный промпт.

Процедурная память выполняет для Sonata роль ассоциативного подсознательного механизма. Ситуация активирует связанный способ мышления без отдельного сознательного перебора всех известных правил.

Основной принцип:

```text
ситуация
→ автоматическая активация подходящей инструкции
→ мышление внутри активированной схемы
```

## 2. Почему инструкция не выбирается агентом

Самостоятельный выбор инструкции моделью создаёт несколько проблем:

- требует отдельного шага планирования или дополнительного вызова;
- заставляет сбрасывать или пересобирать черновое состояние после выбора;
- смешивает мета-задачу выбора способа мышления с самой задачей;
- позволяет модели заявить одну инструкцию, но фактически использовать другую;
- увеличивает вероятность смешивания нескольких несовместимых ролей;
- усложняет воспроизводимость и настройку цепочки.

В новой архитектуре ответственность разделена:

```text
Procedural Memory решает, какая инструкция должна активироваться.
Prompt Assembler вклеивает найденные фрагменты.
Перспектива мыслит и формирует отчёт.
Синтез решает, чему из внутренних мыслей следовать.
```

Перспектива не видит весь реестр и не получает список кандидатов для самостоятельного выбора.

## 3. Граница ответственности

Процедурная память работает только с инструкциями.

Она не хранит и не извлекает:

- факты и документы;
- историю общения;
- пользовательские воспоминания;
- отчёты прошлых циклов;
- знания из внешних источников;
- эмоциональное состояние;
- маршруты моделей и провайдеров.

Общая долговременная память и RAG остаются отдельным проектом и подключаются к Sonata через внешний контракт. Процедурная память является частью ядра Sonata, потому что определяет не содержание воспоминаний, а автоматическую активацию способов мышления.

Это узкий mini-RAG, а не универсальная поисковая система.

## 4. Место в когнитивном цикле

Для каждой активной перспективы инструкция извлекается до вызова модели.

```text
входное событие или запрос
        │
        ▼
Perspective Router
        │
        ▼
Procedural Memory
семантика + лексика + фильтры
        │
        ├── подходящая инструкция
        │
        └── низкое покрытие → протокол n+1
        │
        ▼
Prompt Assembler
identity + invariants + state adapter
+ найденная инструкция или n+1
+ phase contract + output contract
        │
        ▼
единственный вызов перспективы
```

Процедурная память не заменяет роутер перспектив.

- Perspective Router определяет, какие грани Sonata будут активны.
- Procedural Memory определяет, какой способ мышления автоматически активируется внутри каждой уже запущенной грани.

Ошибка роутера может исключить целую точку зрения. Ошибка процедурного поиска влияет только на способ работы уже активной перспективы и может быть обнаружена критической стадией.

## 5. Поиск по фазам

### 5.1. Фаза 1: первичная мысль

Запрос к процедурной памяти формируется на основании:

- текущего запроса или события;
- имени перспективы;
- имени стадии;
- краткого типа задачи;
- релевантных ограничений контекста;
- допустимого смещения от внутреннего состояния Sonata.

Один и тот же пользовательский запрос создаёт отдельный поиск для каждой перспективы.

```text
perspective=logic       phase=primary
perspective=imagination phase=primary
perspective=conscience  phase=primary
perspective=efficiency  phase=primary
perspective=reason      phase=primary
```

Поиск всегда ограничивается инструкциями соответствующей перспективы и стадии.

### 5.2. Фаза 2: внутренняя критика

Инструкция критики выбирается не только по исходной теме, но прежде всего по форме и содержанию первичного отчёта.

Поисковый контекст включает:

- исходную задачу;
- первичный отчёт своей перспективы;
- обнаруженные утверждения и допущения;
- перспективу;
- стадию `critical`.

Так процедурная память может активировать разные способы проверки:

- поиск противоречий;
- проверку цепочки выводов;
- выявление скрытых предпосылок;
- анализ границ применимости;
- построение контр-примера;
- переоценку смысла или цены вывода.

Критическая инструкция должна реагировать на возникшую мысль, а не только на тему запроса.

### 5.3. Фаза 3: метакогнитивное резюме

Суммаризатору могут автоматически активироваться разные схемы структурирования:

- техническое решение;
- изменение философской позиции;
- этическая дилемма;
- практический план;
- созданная n+1 инструкция;
- пересмотр прошлого убеждения;
- нерешённый вопрос.

Процедурная память выбирает форму фиксации, но не заменяет обязательный общий контракт метапамяти.

### 5.4. Фаза 4: Синтез

Синтез не выбирает одну из перспектив как инструкцию. Он остаётся Sonata, принимающей волевое решение.

При необходимости процедурная память может активировать способ организации синтеза, например:

- разрешение противоречий;
- приоритизацию долгосрочных последствий;
- проверку целостности решения;
- переход от размышления к действию.

Такая инструкция помогает организовать акт Синтеза, но не получает право решать вместо Sonata.

## 6. Гибридный поиск

Основной механизм подбора строится на сочетании семантического и лексического поиска.

### Семантический канал

Находит инструкции, близкие к смыслу ситуации, даже когда формулировки не совпадают.

### Лексический канал

Учитывает:

- ключевые слова;
- точные выражения;
- технические термины;
- отрицательные маркеры;
- явные триггеры;
- обязательные условия.

### Структурные фильтры

До ранжирования исключаются инструкции, не соответствующие:

- перспективе;
- фазе;
- статусу активности;
- типу входа;
- ограничениям применения.

### Итоговое ранжирование

Конкретная формула будет определена при реализации, но должна учитывать как минимум:

```text
final_score =
    semantic_score
  + lexical_score
  + trigger_bonus
  + context_compatibility
  + state_bias
  + configured_priority
  - exclusion_penalty
```

Семантическая близость является основным каналом, но не должна единолично определять результат. Ключевые слова и условия защищают от выбора красивой, но неприменимой инструкции.

## 7. Роль состояния Sonata

Внутреннее и эмоциональное состояние может смещать ранжирование, но не должно загрязнять основную поисковую строку полным описанием состояния.

Состояние передаётся как отдельный bias. Например:

- тревога повышает вес способов проверки риска;
- любопытство повышает вес исследовательских и n+1 подходов;
- усталость повышает вес простых и устойчивых методов;
- гнев повышает чувствительность к противоречиям и неэффективности;
- доверие повышает вес кооперативных и долгосрочных решений.

Смещение не является жёсткой командой. Оно влияет на доступность ассоциации, но не подменяет смысл задачи и структурные ограничения.

## 8. Формат инструкции

Каноническая инструкция хранится как отдельная адресуемая сущность.

Минимальные поля:

```yaml
id: logic.system_analysis
name: Системный анализ
perspective: logic
phase: primary
status: active

semantic_description: >
  Анализ сложной системы через компоненты, связи,
  ограничения, входы, выходы и потоки данных.

keywords:
  - архитектура
  - система
  - компоненты
  - взаимодействие

positive_conditions:
  - задача содержит несколько взаимодействующих сущностей

negative_conditions:
  - требуется только краткое определение

instruction: >
  Представь ситуацию как систему. Выдели компоненты,
  связи, ограничения, входы, выходы и точки отказа.

output_contract: system_map
priority: 0.8
compatible_modifiers: []
version: 1
```

Канонические файлы инструкций являются источником истины. Векторный и лексический индексы являются производными представлениями и могут быть полностью пересозданы.

## 9. Что попадает в промпт

Всегда подключаются:

```text
identity
invariants
phase contract
output contract
```

Динамически подключаются:

```text
одна основная инструкция
опционально один совместимый модификатор
```

Условно подключается:

```text
n+1 protocol
```

В контекст модели не должны попадать:

- полный реестр инструкций;
- длинный список альтернатив;
- внутренние поисковые оценки;
- инструкции других перспектив;
- инструкции других фаз без явной необходимости.

По умолчанию выбирается одна основная инструкция. Дополнительный модификатор допускается только при явной совместимости и не должен превращать промпт в новый монолит.

## 10. Принцип n+1

Процедурная память возвращает не только лучшую инструкцию, но и оценку покрытия.

```json
{
  "instruction_id": "logic.system_analysis",
  "score": 0.84,
  "coverage": "sufficient"
}
```

Если ни одна инструкция не проходит установленный порог:

```json
{
  "instruction_id": null,
  "score": 0.31,
  "coverage": "insufficient"
}
```

В этом случае Prompt Assembler не просит перспективу выбирать из известных вариантов. Вместо обычной инструкции он автоматически вклеивает протокол n+1.

Перспектива в рамках того же единственного вызова должна:

1. создать разовый способ мышления для текущей ситуации;
2. дать ему имя и краткое определение;
3. объяснить, почему известные инструкции не покрыли задачу;
4. применить новый способ сразу;
5. вернуть описание разовой инструкции в структурированных метаданных.

Разовая инструкция не добавляется в активный индекс автоматически.

В память сохраняются:

- созданная инструкция;
- поисковый контекст;
- причина недостаточного покрытия;
- первичный результат;
- критическая оценка;
- итоговая полезность.

Отдельный процесс развития может позже предложить повышение успешной инструкции до постоянной. Такое изменение должно быть явным, проверяемым, версионируемым и обратимым.

## 11. Результат поиска

Минимальный контракт результата:

```json
{
  "perspective": "logic",
  "phase": "primary",
  "instruction_id": "logic.system_analysis",
  "instruction_version": 1,
  "semantic_score": 0.79,
  "lexical_score": 0.68,
  "final_score": 0.84,
  "coverage": "sufficient",
  "modifier_ids": [],
  "n_plus_one": false
}
```

Поисковые оценки используются оркестратором и телеметрией, но не обязаны передаваться языковой модели.

## 12. Ошибки и резервное поведение

Низкое покрытие и техническая ошибка поиска являются разными состояниями.

### Низкое покрытие

Поиск отработал корректно, но подходящей инструкции нет. Активируется n+1.

### Техническая ошибка

Индекс недоступен, повреждён или не может выполнить запрос. В этом случае используется минимальная базовая инструкция перспективы, а ошибка явно записывается в телеметрию.

Техническая ошибка не должна маскироваться под творческое срабатывание n+1.

### Неоднозначность

Несколько инструкций имеют близкие оценки. Система применяет детерминированное правило разрешения, например приоритет, специфичность и версию. Перспективе не передаётся список для самостоятельного выбора.

## 13. Телеметрия и развитие

Для каждого поиска фиксируются:

```text
request_id
perspective
phase
normalized_query
retrieved_instruction_id
instruction_version
semantic_score
lexical_score
final_score
coverage
considered_alternatives
applied_modifiers
state_bias
n_plus_one_activated
retrieval_latency
critical_verdict
later_quality_assessment
```

Эти данные позволяют обнаружить:

- инструкции, которые постоянно выбираются ошибочно;
- инструкции, которые критическая стадия регулярно отвергает;
- дублирующиеся способы мышления;
- неиспользуемые инструкции;
- области, где часто срабатывает n+1;
- вредное влияние отдельных эмоциональных смещений;
- необходимость изменить пороги или веса поиска.

Процедурная память должна улучшаться на основании наблюдаемого поведения, а не только ручного ощущения качества промптов.

## 14. Независимость от реализации

Этот документ не закрепляет:

- конкретную embedding-модель;
- конкретный алгоритм лексического поиска;
- конкретную векторную базу;
- язык программирования;
- формат сериализации;
- точную формулу ранжирования;
- числовые пороги достаточного покрытия.

Допустимы встроенный индекс, локальная библиотека или небольшая специализированная база. Тяжёлый внешний RAG для этой задачи не требуется.

Неизменными остаются принципы:

- инструкция активируется до вызова перспективы;
- агент не выбирает её самостоятельно;
- поиск является гибридным;
- реестр не вклеивается целиком;
- n+1 активируется при реальном недостатке покрытия;
- индексы являются производными от канонических инструкций;
- процедурная память работает только со способами мышления.

## 15. Краткое каноническое определение

> Процедурная память Sonata - это внутренний гибридный механизм ассоциативной активации инструкций. Он до начала генерации находит подходящий способ мышления для конкретной перспективы и стадии, вклеивает только необходимую инструкцию, а при недостаточном покрытии автоматически активирует протокол n+1. Перспектива не выбирает роль сама: она начинает мыслить уже внутри вызванной схемы.
